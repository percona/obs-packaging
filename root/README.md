This directory is the root of the OBS packaging tree for Percona products.
Each subdirectory corresponds to an OBS project, with the hierarchy mirroring the OBS project name structure
(e.g. `ppg/17` maps to the OBS project `<org>:ppg:17`).

## Top-level structure

```
root/
├── common/                 # shared packages used across products
│   ├── deps/
│   │   ├── build/          # build-time dependencies (Go toolchain, OBS source services, …)
│   │   └── runtime/        # runtime dependencies shared across products (e.g. percona-telemetry-agent)
│   └── containers/         # shared container base images
├── <product>/              # one directory per Percona product, e.g. ppg/, psmdb/
│   ├── releases/           # release definitions (see below)
│   └── <major-version>/    # one directory per major product version, e.g. 17/
│       ├── <package>/      # source packages for this version
│       ├── containers/     # container images for this version
│       └── tarballs/       # tarball artifacts for this version
└── project.yaml            # root OBS project configuration
```

Current products:

| Directory | Product |

| `ppg/` | Percona Software for PostgreSQL |

Additional products (e.g. `psmdb/` for Percona Server for MongoDB) follow the same layout.

## Common projects

- **`common/deps/build/`** — build-time dependencies shared across all products (Go toolchain, OBS source
  services such as `obs-service-tar_scm`). Product projects declare a path dependency on this project so
  its packages are available at build time.
- **`common/deps/runtime/`** — runtime packages required by product packages across all products
  (e.g. `percona-telemetry-agent`). Each `<major-version>/` subproject that needs these packages should
  aggregate them via an `_aggregate` file, so that the RPM or Debian repository generated by OBS is
  self-contained and consumers do not need to add a separate repository to satisfy runtime dependencies.
- **`common/containers/`** — shared container base images consumed by product container projects.

## Product project layout

Each product directory contains:

### `releases/`

Release definitions. Each subdirectory represents one released version and contains a `release.yaml`
plus the `project.yaml` files that define the OBS release project topology.

```
releases/
└── <name>/                    # one subdirectory per release, e.g. 17.9/
    ├── release.yaml           # release pointer
    ├── project.yaml           # base release project (builds disabled)
    ├── Updates/
    │   └── project.yaml       # Updates subproject (builds disabled)
    └── <subproject>/          # one per source subproject, e.g. containers/
        └── project.yaml       # release subproject (builds enabled for images)
```

Each subdirectory name identifies a release. The convention is to use the product minor version
(e.g. `17.9`), but any descriptive name works.

The `release.yaml` format:

```yaml
repository: ${PERCONA_OBS_PACKAGING_REPO}
revision: <percona-product>/17.9    # e.g. ppg/17.9 — the git tag
project: <percona-product>:17       # e.g. ppg:17 — OBS source project
```

| Field | Description |
|---|---|
| `repository` | URL of this git repository. Use `${PERCONA_OBS_PACKAGING_REPO}` to inherit from the CI environment. |
| `revision` | Git tag in `repository` whose packaging sources were used for this release. Convention: `<product>/<MAJOR.MINOR>` (e.g. `ppg/17.9`). |
| `project` | OBS source project to release from (relative to `rootprj`). |

#### Cutting a release

Use the `project release` command — it generates all required files, commits them, and
prompts you to open a pull request:

```sh
./percona-obs -P <profile> project release ppg:17 17.9
```

The command fetches the source project's build topology from OBS, creates the release
directory with all `project.yaml` and `release.yaml` files, and commits everything.
See `docs/PERCONA_OBS_TOOL.md` for the full workflow description.

The release tag (`ppg/17.9`) and the OBS release project are created automatically
by CI when the pull request is merged — do not create the tag manually.

### `<major-version>/`

One subdirectory per major product version under active development (e.g. `17/` for PostgreSQL 17).
The naming convention is the major version number, but other schemes are allowed.

Inside a major version directory:

| Subdirectory | Contents |
|---|---|
| `<package>/` | Source packages for this version (one subdirectory per package) |
| `containers/` | Container image definitions for this version |
| `tarballs/` | Tarball artifact definitions for this version |

Each package directory contains the packaging sources split by format:

```
<package>/
├── obs/        # OBS service files (_service, _aggregate, …)
├── rpm/        # RPM spec and supporting files
└── debian/     # Debian packaging files
```

## project.yaml

Each project directory may contain a `project.yaml` file that defines the OBS project metadata,
build repositories, and project configuration. The root `project.yaml` defines the top-level project
and the repositories available to all subprojects.
