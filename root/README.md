This directory is the root of the OBS packaging tree for Percona products.
Each subdirectory corresponds to an OBS project, with the hierarchy mirroring the OBS project name structure
(e.g. `ppg/staging/17` maps to the OBS project `<org>:ppg:staging:17`).

Each product uses a three-tier layout: `devel/<V>` (dev-branch builds, manually curated subset),
`staging/<V>` (full package set, tag builds, QA/release candidate — this is what `releases/` releases
from), and `releases/<V>` (immutable, read-only release snapshots). See "Product project layout" below.

## Top-level structure

```
root/
├── common/                 # shared packages used across products
│   ├── deps/
│   │   ├── build/          # build-time dependencies (Go toolchain, OBS source services, …)
│   │   └── runtime/        # runtime dependencies shared across products (e.g. percona-telemetry-agent)
│   └── containers/         # shared container base images
├── <product>/              # one directory per Percona product, e.g. ppg/, psmdb/
│   ├── releases/           # release definitions (see below)
│   ├── staging/
│   │   ├── project.yaml       # staging container project configuration
│   │   └── <major-version>/   # full package set for this version, e.g. 17/
│   │       ├── <package>/     # source packages for this version
│   │       ├── containers/    # container images for this version
│   │       └── tarballs/      # tarball artifacts for this version
│   └── devel/
│       ├── project.yaml       # devel container project configuration
│       └── <major-version>/   # manually curated dev-branch subset for this version
│           └── <package>/     # Class A (full copy) or Class B (obs/_link only) package
└── project.yaml            # root OBS project configuration
```

Additional products (e.g. `psmdb/` for Percona Server for MongoDB) follow the same layout.

## Common projects

- **`common/deps/build/`** — build-time dependencies shared across all products (Go toolchain, OBS source
  services such as `obs-service-tar_scm`). Product projects declare a path dependency on this project so
  its packages are available at build time.
- **`common/deps/runtime/`** — runtime packages required by product packages across all products
  (e.g. `percona-telemetry-agent`). Each `staging/<major-version>/` subproject that needs these packages should
  aggregate them via an `_aggregate` file, so that the RPM or Debian repository generated by OBS is
  self-contained and consumers do not need to add a separate repository to satisfy runtime dependencies.
- **`common/containers/`** — shared container base images consumed by product container projects.

## Product project layout

Each product directory contains:

### `releases/`

Release definitions. One subdirectory per PG major version contains `release.yaml`,
`project.yaml`, `CHANGELOG.md`, and a subproject directory per source subproject.

```
releases/
└── 17/                         # one directory per PG major version
    ├── release.yaml            # list of release tags
    ├── project.yaml            # ppg:releases:17 OBS project (builds disabled)
    ├── CHANGELOG.md            # keep-a-changelog, all releases for this major
    └── containers:ubi9/        # one per source subproject (colon-named)
        └── project.yaml        # builds disabled; binaries copied via osc release
```

The `release.yaml` format:

```yaml
repository: ${PERCONA_OBS_PACKAGING_REPO}
project: ppg:staging:17         # OBS source project (relative to rootprj)
releases:
  - ppg/17.9-1                  # first release
  - ppg/17.9-2                  # update release
  - ppg/17.10-1                 # minor version bump (counter resets to 1)
```

| Field | Description |
|---|---|
| `repository` | URL of this git repository. Use `${PERCONA_OBS_PACKAGING_REPO}` to inherit from the CI environment. |
| `project` | OBS source project to release from (relative to `rootprj`). |
| `releases` | List of git tags, one per release event. The last entry is always current. |

Release IDs follow the pattern `MAJOR.MINOR-N` where `N` is the release counter
for that minor version (resets to 1 when the minor version changes).

#### Cutting a release

Use the `project release` command — it auto-derives the release ID from OBS,
creates or updates all required files, commits them, pushes a branch, and opens
a review PR:

```sh
# Fully automatic
./percona-obs -P <profile> project release ppg:staging:17

# Override release ID explicitly
./percona-obs -P <profile> project release ppg:staging:17 --release-id 17.9-1
```

The command fetches the source project's build topology from OBS, diffs package
versions against the previous release to generate `CHANGELOG.md`, and commits
everything. See `docs/PERCONA_OBS_TOOL.md` for the full workflow.

The git tag (e.g. `ppg/17.9-1`) is created automatically by `sync-main.yml`
when the merge commit lands on `main`. That tag triggers `obs-release.yml`,
which copies binaries to the OBS release project and creates a GitHub release.

### `staging/<major-version>/`

One subdirectory per major product version (e.g. `17/` for PostgreSQL 17). This is the full package
set: tag-based builds, used for QA and release candidates. `releases/` releases are cut from here.
The naming convention is the major version number, but other schemes are allowed.

Inside a staging major-version directory:

| Subdirectory | Contents |
|---|---|
| `<package>/` | Source packages for this version (one subdirectory per package) |
| `containers/` | Container image definitions for this version |
| `tarballs/` | Tarball artifact definitions for this version |

Each package directory contains the packaging sources split by format:

```
<package>/
├── obs/        # OBS service files (_service, _aggregate, …)
├── rpm/        # RPM spec and supporting files
└── debian/     # Debian packaging files
```

#### `tarballs/`

Binary-tarball builds (OBS `simpleimage` format) for air-gapped / unsupported-distro
installs, replicating the official Percona tarball layout file for file. One
subproject (`ppg:staging:<V>:tarballs`) with a single `percona-postgresql-tarball`
package, built across two repositories — one per SSL variant, each stacked on a
different EL base of `ppg:staging:<V>`:

| Repository | Base | Host ABI targeted |
|---|---|---|
| `ssl1.1` | RockyLinux_8 | glibc ≥ 2.28, OpenSSL 1.1 (stock and RHEL-fork hosts) |
| `ssl3` | RockyLinux_9 | glibc ≥ 2.34, ALL OpenSSL 3.x hosts |

The `ssl3` promise ("runs on any OpenSSL 3.0 host") holds on the EL9 base —
whose own OpenSSL is 3.5.x since Rocky 9.8 — because the built binaries are
pinned to `OPENSSL_3.0.0` symbol-version nodes at the source: staging
`percona-postgresql` patches pgcrypto to avoid an OpenSSL 3.4-only API, and
`percona-tarball-python3` patches CPython's `_ssl`/`_hashlib` the same way, so
`plpython3u`'s `import ssl` works on every 3.x host (the official tarball's
own python fails that on 3.0 hosts). The builder's verification gate enforces
exactly that per variant. (An interim Ubuntu 22.04 deb-based `ssl3` was tried
and abandoned: the PGDG deb layout is non-relocatable.)

Each artifact contains eleven top-level components, matching the official
layout: `percona-postgresql<V>`, `percona-patroni`, `percona-pgbackrest`,
`percona-pgbouncer`, `percona-pgpool-II`, `percona-pgbadger`, `percona-etcd`,
`percona-haproxy`, and the bundled `percona-python3` / `percona-perl` /
`percona-tcl` language runtimes.

Per-repository differences (prjconf resolution hints) are handled with
`%if "%_repository" == "..."` conditionals in the project config; the
`simpleimage` recipe is variant-independent and its `%build` runs the single
builder script, `build-tarball.sh`. The script stages all components under
`/opt/percona-*`, runs the verification gate (unresolved-soname audit, a
per-variant OpenSSL host-ABI audit, a compiled-socket-dir byte-string audit,
a python-bytecode audit, the 11-component inventory and zero-env smoke
probes) and creates the artifact itself: it derives the official tarball name
at build time (the SSL variant is mapped from the buildroot's EL major in
`/etc/os-release`, with a glibc `%dist`-tag fallback) and writes it directly
into the OBS result directory (`/usr/src/packages/OTHER`), bypassing the
recipe's own fixed-name tar step (`#!NoTarBall`). Both repositories publish
their results, so the `.tar.gz` files are downloadable from the OBS publish
tree.

Behavioral parity with the official from-source tarball — no wrappers, no
environment variables:

- **Compiled `/tmp` socket defaults.** The builder rewrites the RPM-compiled
  `/run/postgresql` socket-dir C string constants to `/tmp` in place in every
  bundled ELF (same-length NUL-padded, so no offsets change) — the server,
  `initdb`'s generated config (any invocation form) and every libpq client
  (psql, pgbench, pg_dump, pg_isready, ...) default to a `/tmp` unix socket,
  exactly like the official binaries. No `PGHOST`, no `/run/postgresql`.
- **Zero-env PL languages.** `plperl.so`/`pltcl.so`/`plpython3.so` carry
  RUNPATHs pointing at from-source `/opt`-prefixed runtimes built in
  `ppg:common:deps` (`root/ppg/common/deps/`): `percona-tarball-perl`,
  `percona-tarball-tcl` (8.6.10) and `percona-tarball-python3` (3.12.13).
  Every path (`@INC`, `TCL_LIBRARY`, `sys.prefix`) is compiled into those
  runtimes, so all three PLs work even under a bare `postgres -D` start from
  an empty environment. The only wrapper left in the artifact is psql's
  host-readline shim (the official tarball ships the same one).
- **Perl version constraint (documented, accepted).** The bundled perl is
  5.26.3 (`ssl1.1`) / 5.32.1 (`ssl3`), not the official tarball's 5.38:
  `plperl.so` is ABI-tied to the distro libperl the PG RPM was built against
  (DT_NEEDED `libperl.so.5.26`/`.5.32` plus the distro perl's config), so the
  bundled runtime must match it exactly. The official tarball ships 5.38
  because it builds PostgreSQL itself against its own perl — doing that here
  would change the shipped RPM product.
- **No python bytecode.** The artifact ships zero `.pyc`/`__pycache__` files
  (the official tarball ships none either); gate-enforced.

Host prerequisites (beyond the glibc/OpenSSL floors above): a non-root OS
user to run the server (conventionally `postgres`); host readline for
interactive psql (`libreadline8`/`libreadline8t64` on Debian-family hosts —
the psql wrapper LD_PRELOADs it); tzdata (`/usr/share/zoneinfo` — the server
is built with system tzdata; absent on some minimal images); the documented
install step of copying `percona-{python3,perl,tcl}` to `/opt` (the PL
RUNPATHs and the runtimes' compiled-in paths point there — unchanged from the
official docs); and, for GSSAPI/Kerberos authentication only, host krb5
*configuration* (`/etc/krb5.conf`) — the krb5 libraries themselves are
bundled. No `/run/postgresql` directory and no environment variables are
needed.

Operational note: if the `ssl1.1` SSL-ABI audit ever fires on
`OPENSSL_1_1_1b`-class version nodes via libkrb5/libgssapi/libssh, the EL8
distro has rebased krb5/libssh past the percona `-NN.percona` rebuilds in
`ppg:common:deps` — bump those rebuilds.

### `devel/<major-version>/`

A manually curated subset of `staging/<major-version>/`, built from development branches instead of
release tags. Its purpose is to let day-to-day dev-branch work be built and tested against the rest of
the staging package set without disturbing staging itself.

Membership is manual: whoever adds a package to `devel/<V>/` must also add its direct build/runtime
dependents, since a dependent left out of devel would otherwise silently link against a staging-built
(possibly ABI-incompatible) copy of the package being changed.

Each package in `devel/<V>/` is one of two classes:

- **Class A (full copy)** — the entire staging package directory (`rpm/`, `debian/`, `obs/`, and
  `package.yaml` if present) is duplicated into `devel/<V>/<package>/`, with `obs/_service`
  retargeted from a release tag to a development branch. The packaging is deliberately duplicated
  so it can be edited independently of the staging copy while the dev branch is being worked on.
  `devel/<V>/macros.yaml` is likewise a copy of staging's `macros.yaml`, so `%!{VAR}` macros in the
  copied packaging files resolve identically in both tiers.
- **Class B (link only)** — the package directory contains only an `obs/_link` file pointing at the
  staging package, e.g.:

  ```xml
  <link project="${OBS_ROOTPRJ}:ppg:staging:18" package="some-package"/>
  ```

  This rebuilds the unmodified staging package in the devel context, so it links against the other
  devel binaries instead of staging's.

`devel/<major-version>/project.yaml` repository paths list `ppg:staging:<V>` first, followed by a copy
of staging's own upstream path list (PGDG, …, with the base distro last). This duplication is required
because OBS only expands the *last* repository path in a project's path list transitively — so if
staging's upstream path were left implicit (relying on it being pulled in through `ppg:staging:<V>`),
it would silently resolve to nothing.

Graduation: when a development cycle concludes and a new release tag is cut, the staging package's
`obs/_service` revision is bumped to the new tag (staging always builds from tags), and the devel
entry (Class A or B) is removed — or repointed at the next development branch if work continues.

## project.yaml

Each project directory may contain a `project.yaml` file that defines the OBS project metadata,
build repositories, and project configuration. The root `project.yaml` defines the top-level project
and the repositories available to all subprojects.
